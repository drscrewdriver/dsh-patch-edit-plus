# История изменений

## [0.4.0] — 2026-10-09

### Добавлено

- **Единая версия для всех линий хостов.** Одна версия (0.4.0) обслуживает все хосты DSH от `0.1.0-rc.8` до `0.2.0-rc.2` — все 15 rc плюс desktop; диапазоны peer перечисляют все 15 rc, а `engines.dsh` объявляет `>=0.1.0-rc.8`. Выведенные из эксплуатации compat-ветки (`compat/0.1.2`, `compat/0.1.5`, `compat/0.1.7`) и схема разделения по `main` удалены; после публикации npm dist-tag'и `latest`, `dsh-0.2.0`, `dsh-0.1.7`, `dsh-0.1.5` и `dsh-0.1.2` сходятся на 0.4.0.
- **Три поколения настроек в одной кодовой базе**: декларативный `.volatile()` плюс перерегистрация через `loader/volatile-update` на 0.1.7+ (и desktop); экземплярные `settings.installSection`/`register` на 0.1.2/0.1.5; модульный `installSettingsSection` из `@deepseek-ai/dsh-settings` на 0.1.0/0.1.1. Карточка конфигурации на странице плагина (клиентская половина) присутствует только на 0.1.7+/desktop и на старых линиях изящно отсутствует.
- Путь авторинга `defineTool` с мягкой деградацией fs: на линиях, где в `fs` нет write-intent, запись деградирует до прямой с одним `console.warn` вместо сбоя.
- Матрица тайпчека по шести линиям, плюс smoke-шлюз, покрывающий сценарии изящного отсутствия.

### Изменено

- **Ломающее изменение: `allowCodexPatch` по умолчанию теперь `false`** (включение вручную, выровнено с линией 0.2.0; старое значение по умолчанию на линии 0.1.7 было `true`). Существующим пользователям линии 0.1.7 нужно включить его вручную после обновления до 0.4.0.

## [0.3.0] — 2026-09-29

### Изменено

- **Поддержка линии DSH 0.2.0 (ветка `compat/0.2.0`).** Диапазоны peer-зависимостей и `engines.dsh` (в обоих манифестах) теперь объявляют `>=0.2.0-rc.1 <0.2.1-0`; версия 0.3.0. devDependencies фиксируют реальную типовую базу `0.2.0-rc.1`, а скрипт перекрёстной проверки переведён на `npm run typecheck:0.2.0` (устанавливает реальные peer-пакеты из registry). Хосты 0.1.x по-прежнему обслуживаются веткой `compat/0.1.7` / dist-tag `dsh-0.1.7`.
- **Delete/Move переведены на актуальный API shell-исполнителя.** Между линиями хостов 0.1.2 и 0.1.7 `ShellExecutor.run(spec)` был переименован в `execute(spec)` — с возвратом дескриптора `ShellProcess` и foreground-проекцией `result()`. Старый пин devDependency (`0.1.2-rc.1`) маскировал это: пакет линии 0.1.7 (0.2.1) зелено проходил тайпчек против устаревшей базы, а на реальных хостах 0.1.7+ его утинная типизация на основе `run` никогда не совпадала, из-за чего Delete/Move деградировали до структурированной ошибки UNSUPPORTED. Эта линия вызывает `shell.execute(...)` и ожидает `execution.result()`; исполнитель распознаётся по `execute`.

## [0.1.2] — 2026-09-19

### Исправлено

- **Секция настроек так и не была зарегистрирована.** Пространство имён настроек `patch_edit_plus` содержит подчёркивание, которое отклоняется шаблоном пространств имён `dsh-settings` (`^[a-z][a-z0-9-]*$`), поэтому `register()` падал до всякой записи — ни в панели, ни в `~/.dsh/settings.yaml` запись настроек не появлялась. Переименовано в `patch-edit-plus` (миграция не нужна: старая секция не могла существовать в принципе).
- **Изменения конфигурации из слоя настроек никогда не доходили до инструмента.** Хуки `setSource`/`onChange` были заглушками, а разрешённая конфигурация мемоизировалась один раз при загрузке. Теперь плагин потребляет разрешённый источник: каждое подтверждённое изменение настроек (или legacy-watch `register`) заново разрешает конфигурацию и перерегистрирует инструмент — предварительно уничтожая старую регистрацию, поскольку перерегистрация поверх живого имени молча его переименовывает. `allowCodexPatch` и все остальные поля теперь переключаются из панели настроек DSH и вступают в силу немедленно, причём описание инструмента (список принимаемых стилей патчей) остаётся синхронным; перезапуск процесса не требуется. При отключении сервиса настроек происходит откат к записи композиции, а повторное суждение идемпотентно (сравнивается вся разрешённая конфигурация, а не одно поле).

## [0.1.1] — 2026-09-17

### Исправлено

- **Каждая запись отклонялась под `workspace-write`.** Инструмент не передавал `sandboxPolicy` на вызов, поэтому принуждающая файловая система откатывалась к `ctx.sandboxPolicy.resolve()` без области видимости — корень рабочей области РАЗВЁРТЫВАНИЯ (каталог запуска сервера) вместо cwd сессии. Путь, явно лежащий внутри рабочей области сессии, не проходил проверку охвата и возвращал `file access denied under workspace-write mode`, даже в сессии `danger-full-access`, где режим даже не считывался. Теперь политика разрешается при каждом вызове с вызывающей сессией в области видимости (`resolve({ session })`) и проставляется на каждую запись и каждый shell-запрос Delete/Move — в точности как у нативных инструментов `write`/`edit`. Теперь соблюдаются обе половины режима: переопределение `sandbox/mode` сессии и её cwd как корень рабочей области.
- Разрешение путей и ограждение теперь используют один корень: план разрешает каждую цель относительно `workspaceRoot` политики (с откатом к cwd сессии), так что путь, который пишет движок, — это путь, который измеряет ограждение.

## Unreleased

### Добавлено

- Единственный доступный модели инструмент `apply_patch`, принимающий git/unified diff (по умолчанию) и синтаксис `apply_patch` от Codex (по явному включению через `allowCodexPatch`).
- Автоопределение формата с действенной подсказкой, когда приходит распознанный, но отключённый стиль.
- Операции Add / Update (multi-hunk) / Delete / Move; Delete и Move идут через учитывающий sandbox `ctx.shell`, пути передаются только через переменные окружения.
- Двухфазный движок «всё-или-ничего»: полная проверка в режиме только чтение (локализация контекста с тремя уровнями допуска, удержание в рабочей области, отклонение symlink, обнаружение дублирующихся путей) перед любой записью.
- Официальная write-intent-последовательность при каждой записи: водопад `fs/write-intent` → защищённый `writeText` → эмиссия `fs/observed`, так что барьер «сначала прочти, потом пиши» действует и для записей патчей.
- Четырёхэлементная диагностика несовпадения хунка (файл + индекс хунка, начало поиска, ожидаемое превью с видимыми пробелами, фактический фрагмент) плюс адресная подсказка.
- Параметр `dryRun` и настройка `dryRunByDefault`.
- Группированный вывод с семантикой Codex (added → modified → deleted) с диффами по файлам, ограниченными `maxDiffBytes`, и устойчивым к повторному проигрыванию `presentationMeta`.
- Трёхуровневая защита от конфликтов имён инструментов (`rename` по умолчанию / `skip` / `fail`), чтобы столкновения имён с другими провайдерами `apply_patch` никогда не ломали запуск DSH.
- Совместимость с DSH `0.1.2-rc.1` ~ `0.1.5-rc.2`: единый путь кода для авторинга инструментов плюс статическая проверка `typecheck:0.1.5` против peer-пакетов 0.1.5-rc.2; двух-API-фолбэк настроек (`installSection` / `register`).
